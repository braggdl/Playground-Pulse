1. Project introduction

Playground Pulse is a kid-friendly park finder built to give families better information than a general map search can provide. Instead of only showing where a park is, it helps users understand whether that park matches a child’s age, a family’s safety expectations, and the realities of current conditions.

Name and purpose

Playground Pulse is a web application focused on playground discovery. Its main purpose is to help families make faster, safer decisions about where to go by centralizing child-friendly filters, current crowd information, and community reporting in one place.

Intended users

The primary users are parents and caregivers. The application also supports Park Admin and Site Admin roles so trusted users can maintain park information, review reports, manage equipment status, and moderate community content.

The problem

General-purpose mapping tools do not answer the questions families actually ask before a trip: Is there toddler-safe equipment? Are the restrooms open? Is the park fenced? Is it too crowded right now? Playground Pulse addresses that gap with park-specific, family-focused information.

What the team built

Our team built a role-aware experience with account creation and login, searchable park listings, child-friendly filters, crowd reporting, safety and maintenance reporting, profile management, community features, favorites, photo uploads, and administration workflows supported by Firebase services.

Authentication and Roles

Registration, login, logout, forgot-password recovery, protected pages, and role-aware permissions for Parent, Park Admin, and Site Admin users.

Park Discovery

Search by name or location, then narrow results with filters for age groups, fencing, restrooms, shade, and maintenance status.

Live Park Context

Crowd reporting, busy-level calculation, seven-day crowd history, and a map view to help families judge current park conditions.

Community Input

Safety and maintenance reports, park reviews, ratings, photo uploads, and favorites saved to user profiles.

Administration

Park management, equipment status updates, moderation workflows, audit logging, notifications, and park-admin assignment tools.

2. Website showcase

Instead of listing every screen in isolation, these workflows show what a user is trying to accomplish from start to finish and what the application does in support of that task.

Workflow 1

Create an account and find a good-fit park

User goal

A parent wants to create an account, sign in, search nearby parks, and quickly narrow the list to places that fit their child’s age and the family’s needs.

What we implemented

The login page supports registration, sign-in, and password recovery. After login, the dashboard provides search, multi-filter discovery, pagination, and park cards that lead into richer park details.

Behind the scenes

Firebase Authentication manages identity, while Firestore stores user roles and park records. Search and filter behavior reads structured park data and keeps the UI responsive with loading, empty, and retry states.

Feature we are proud of

The discovery flow stays focused on family-specific decisions rather than generic mapping. The combination of role-aware access and child-friendly filters makes the app feel purpose-built.

Workflow 2

Open a park and contribute current information

User goal

A signed-in user wants to decide whether a park is suitable right now, then contribute helpful information for other families by reporting crowd levels, safety concerns, reviews, or photos.

What we implemented

Users can open park details, submit crowd reports, view busy-level badges, review seven-day crowd trends, leave a rating, upload a photo, report safety or maintenance issues, and save parks to favorites.

Behind the scenes

Recent crowd reports are stored and used to compute a recency-weighted busy level. Safety reports, reviews, notifications, and favorites are persisted in Firestore, while photo uploads use Firebase Storage with type and size validation.

Feature we are proud of

The app turns a simple park listing into a living record of community knowledge. The crowd, safety, and review features make the park detail view meaningfully actionable.

Workflow 3

Manage parks and moderate community activity

User goal

An administrator wants to keep park records trustworthy by updating park data, handling reports, assigning admins, and moderating community content.

What we implemented

Park Admin and Site Admin users can create and edit park records, update equipment status, manage safety-report workflows, moderate reviews, and use the administration console for assignments and audit visibility.

Behind the scenes

Role checks govern which actions are available in the interface and which updates can be persisted. Administrative actions also write audit events and trigger in-app notifications when report statuses change.

Feature we are proud of

The administration path demonstrates that the project is more than a front-end mockup. It shows how operational workflows, permissions, and data integrity were part of the design from the start.

3. Challenges and incomplete work

This project grew from a straightforward park finder into a more complex role-aware application. Several features took longer than expected because they had dependencies across authentication, data design, UI states, and team integration.

Challenge: role-aware behavior touched many surfaces

Authentication was not only about sign-in. Once different user roles existed, every create, edit, moderation, and admin path needed both UI gating and service-level checks. That made seemingly simple features more expensive to wire correctly.

Took longer than expected: advanced Firebase-backed features

Features like busy-level calculation, notifications, favorites, photo uploads, and admin assignment each depended on different collections, rules, and validation patterns. The integration cost across those pieces was higher than it appeared at the feature-list level.

Did not work exactly as first imagined

Some workflows needed iteration after implementation, especially park detail interactions, popup behavior, and responsive layout tuning. The team adjusted UI structure as the dashboard became denser and more interactive across sprints.

Incomplete or deferred work

Email-based notification delivery, broader analytics, and deeper polish around some administrative experiences remain incomplete. If time continued, those areas would need another pass for refinement, hardening, and usability validation.

4. Interesting lessons

The most useful lessons came from the parts of the project where implementation details changed our original assumptions about scope, architecture, and collaboration.

Firebase structure matters early

Collections, relationships, and security assumptions influence feature complexity long before the UI feels complete. A small schema decision can affect reporting, favorites, notifications, and moderation later.

Role-based UX is an architecture problem

Roles cannot be treated as a cosmetic toggle. They shape routes, buttons, validation, and service rules at the same time, so the best results came from treating authorization as a shared system concern.

Parallel team work needs explicit contracts

Implementation plans, model definitions, and service contracts made it easier to integrate work from different teammates. Without those agreements, later feature merges would have been slower and riskier.

Testing and debugging are tightly linked to workflow design

Features like duplicate crowd-report prevention, password reauthentication, and admin moderation only became reliable after being tested as complete user tasks rather than isolated functions.

AI works best as a scoped development assistant

AI was most helpful when used for structured implementation support, UI iteration, and debugging assistance against clear requirements. It was less useful when the scope or data contracts were still vague.

5. Future improvements

The next phase should focus on the changes that most improve trust, maintainability, and everyday usability rather than simply adding more isolated features.

Highest-priority feature or fix

Strengthen end-to-end admin and moderation workflows

The application already includes administration tools, but those flows would benefit from deeper validation, clearer edge-case handling, and smoother park-scoped moderation behavior.

Quality improvement

Expand testing coverage for full user journeys

The best next quality investment would be more repeatable testing across authentication, role-specific permissions, park detail actions, and responsive layouts.

Redesign or refactor target

Refine the dashboard information architecture

The dashboard now carries search, detail, reporting, community, and map responsibilities. A future refactor should separate those concerns more cleanly without losing quick access to key park actions.

What we would approach differently

Lock shared contracts earlier across sprints

If we repeated the project, we would invest earlier in stable shared data contracts and feature boundaries so advanced Sprint 2 and Sprint 3 work could integrate with less rework.
